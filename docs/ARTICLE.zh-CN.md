# 我把 AI 协作做成了一个 Agent Harness：不是召唤 3 个 Agent，而是设计一套制衡系统

当我们对 AI 提需求时，为什么它有时候看起来很努力，但结果仍然不稳定？

它会写得很快，也会自我检查，甚至会告诉你“已完成”。但真正的问题是：生成者自己检查自己，本质上不够可靠。

于是我把这套方法整理成了一个通用 skill，叫做 Agent Harness。

它的核心不是“多叫几个 Agent 来干活”，而是把一次 AI 工作拆成一套结构化生产系统。

这套系统里有 3 个角色：

1. Planner，规划者
2. Generator，生成者
3. Evaluator，评估者

但还有一个隐藏角色：Coordinator，协调者。

Coordinator 不是三人之一。它更像导演或项目经理，负责保存用户意图、分配角色、控制边界、组织文件交接，并决定什么时候继续迭代、什么时候结束。

## 为什么不是让 3 个 Agent 一起写？

很多人理解多 Agent，会自然想到：“那我是不是开 3 个 Agent，让它们并行想方案？”

这其实很容易失控。

如果 3 个 Agent 都在“生成答案”，它们只是 3 个写手。最后你得到的可能是 3 份相似、冲突、难以合并的产物。

我真正想要的不是“多人写作”，而是“角色制衡”。

Planner 不写代码，不做最终判断。
Generator 负责真正产出。
Evaluator 不参与生产，只负责严格验收。

这三个角色互相隔离，才是关键。

## Planner：只定义“要什么”

Planner 的任务，是把用户一句模糊的需求，扩展成一个高层规格说明。

它要回答目标是什么、用户是谁、范围是什么、什么不做、有哪些约束、什么情况算完成。

但 Planner 不能过早规定技术细节。

因为很多 AI 失败，不是因为不会写，而是因为一开始就被一个过度具体、但其实不准确的方案绑死了。

Planner 应该像一个清醒的产品经理：把问题定义清楚，但不要替工程师乱选实现路径。

## Generator：只做合同内的事情

Generator 是真正干活的人。

但它不能拿到需求就直接开写。它必须先读 Planner 写出来的产品规格，再和 Evaluator 共同确认一份迭代合同。

这份合同定义本轮到底做什么，验收标准是什么，怎么验证，哪些明确不做。

默认情况下，一轮只做一个功能、一个用户流程，或者一个可验收的 vertical slice。不要把一堆不相关的任务塞进同一轮。

Generator 可以自检，但自检只是初步检查，不能作为最终质量门。

生成者的自我检查，不能替代独立评估。

## Evaluator：不是礼貌审稿人，而是严格验收者

Evaluator 是这套系统里最关键的角色。

它不是来夸 Generator 的，也不是来补充建议的。它的任务是独立验证结果是否达标。

能跑测试就跑测试。能点页面就点页面。能看截图就看截图。能查日志就查日志。能复现就复现。

Evaluator 不应该相信 Generator 的自我汇报。它必须自己检查证据。

默认评估维度有四个：

- 设计质量
- 原创性
- 工艺和执行细节
- 功能性

尤其在设计、产品、内容类任务里，AI 很容易做出“看起来完整，但一眼 AI 味”的东西。所以 Evaluator 要特别惩罚模板化、泛化、装饰性过强、没有任务特异性的输出。

对于后端、数据、运维类任务，则可以额外加入正确性、安全性、可观测性、回滚方案、验证路径等维度。

## 最关键的一步：先谈合同

在每一轮构建前，Generator 和 Evaluator 不是直接开始工作，而是先协商合同。

流程是：

Generator 先草拟本轮要交付什么。
Evaluator 加入更严格的验收标准和边界情况。
Generator 可以反驳，说明某些要求超出范围或应该延期。
双方继续通过文件来回交接，直到 Evaluator 标记 AGREED。

只有合同成立，Generator 才开始构建。

这避免了一个常见问题：做完之后才发现大家对“完成”的理解完全不同。

## 为什么用文件交接？

我倾向于让每个角色写文件：

- `10-product-spec.md`
- `20-evaluation-rubric.md`
- `25-iteration-contract.md`
- `30-generation-report.md`
- `40-evaluation-report.md`
- `50-final-summary.md`

这样角色不会混成一团，后续 Agent 也不必继承整个长聊天。每一步都留下证据，可以复盘。当上下文变长、模型开始混乱时，也可以通过交接文档重启一个新 Generator。

这其实是把“上下文管理”从聊天技巧，变成工程结构。

## 流程不是永远固定的

我不认为任何 harness 都应该永久复杂。

每个组件都代表一个假设。

Planner 存在，是因为模型可能会误解需求。
Evaluator 存在，是因为生成者自评不可靠。
迭代合同存在，是因为任务边界容易漂移。
上下文重置存在，是因为长任务里模型可能失去状态。

但如果模型能力变强，某些组件也可以被移除或后移。

例如在更强模型上，可以进入 simplified final review mode：Planner 仍然保留，Generator 可以连续完成更大范围的工作，Evaluator 不再每轮评审，而是在最后做一次严格统一验收。

但有一个底线不能变：生成和评估必须分离。

可以减少流程，但不能让 Generator 自己当最终裁判。

## 结语

AI 时代真正重要的，不只是写一个更长的 prompt。

更重要的是设计一套让 AI 稳定工作的结构。

好的 prompt 是一句话。
好的 skill 是一套习惯。
好的 harness 是一个组织系统。

它让 AI 不只是回答问题，而是按照一种可检查、可复盘、可迭代的方式工作。
