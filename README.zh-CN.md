# Agent Harness Skill：把模型能力装进一套可演化的协作系统

Agent Harness 是一个平台中立的 AI 协作 skill。它参考了 harness engineering 一类实践里的核心思想，但不是对某篇文章或某个实现的复刻；这个仓库把那些思想重新组织成一套可安装、可迁移、可审计的工作协议。

一句话概括：

**同一个模型、同一句需求，结果差异往往不只来自模型本身，而来自你在模型周围搭了什么系统。**

这个 skill 的目标，就是把一次 AI 工作从“让一个 Agent 从头写到尾”改造成一个有分工、有合同、有验收、有复盘的生产流程。

## 这套方法解决什么问题？

很多 AI 任务失败，不是因为模型完全不会做，而是因为工作流本身太松散：

- 用户一句话需求被模型低估，最终产物范围很薄。
- 上游规划太细，一旦技术假设错了，错误会一路传导。
- 生成者自己评价自己，天然容易宽容。
- 主观质量没有被拆成可评分、可反馈、可迭代的信号。
- 验收停留在“看起来完成”，没有真正运行、点击、复现或查日志。
- 长任务里上下文越来越重，模型开始提前收尾或丢失状态。
- Harness 组件越堆越多，却没有验证哪些还真的有用。

Agent Harness 把这些失败模式拆成角色、文件和协议。

## 核心角色

这套系统在一个 agent 内部运行三个隔离角色轮次：

- **Planner / 规划者**：把用户的一句话需求扩展成高层产品/任务规格。
- **Generator / 生成者**：按照合同真正产出代码、文档、设计或其他结果。
- **Evaluator / 评估者**：作为独立裁判，严格验证结果是否达标。

还有一个不计入三角色轮次的宿主角色：

- **Coordinator / 协调者**：组织流程、传递文件、应用系统和仓库约束、仲裁争议、决定继续迭代还是结束。

重点不是“多叫几个 Agent 一起写”。如果所有角色都在生成答案，它们只是多个写手。Agent Harness 真正要建立的是制衡关系：规划、生成、评估彼此隔离。

## 设计原则

### 1. 上游规划要克制

Planner 只回答“要什么”，不抢着规定“怎么做”。

它应该定义目标、用户、范围、非目标、约束、风险和验收标准。但除非约束明确要求，否则不提前指定脆弱的实现细节。

这样做是为了避免错误级联：上游一个看似专业但错误的技术判断，会把后面的生成和评估全部带偏。

### 2. 生成和评估必须分离

Generator 可以自检，但自检只是初步检查。最终质量门必须交给独立 Evaluator。

这是整套方法最重要的底线。让生成者学会严厉批判自己很难；让另一个独立评估器变严格，相对更容易，也更容易调优。

### 3. 主观质量要变成具体评分信号

Evaluator 默认使用四个基础维度：

- **设计质量**：颜色、排版、布局、层级、交互是否形成统一整体。
- **原创性**：是否有任务特定决策，而不是通用模板或明显 AI 套路。
- **工艺**：技术执行、一致性、对比度、可维护性、细节质量。
- **功能性**：用户是否真的能完成核心任务。

权重应该根据模型短板调整。对于设计和产品任务，设计质量与原创性通常更重，因为模型容易生成“精致但通用”的结果。对于工程任务，可以补充正确性、安全性、可观测性、回滚方案、验证路径等维度。

### 4. 每一轮生成前先谈合同

Planner 的规格故意保持高层，因此 Generator 和 Evaluator 需要在每个构建周期前协商一份 `25-iteration-contract.md`。

合同要把高层目标翻译成可测试的本轮交付：

- 本轮目标
- 具体交付物
- 精确验收标准
- 验证方法
- 不做事项
- 文件或产物归属
- 停止条件
- 协商记录

默认一轮只做一个功能、一个用户可见流程，或一个可验收的 vertical slice。Generator 先提出方案，Evaluator 加入更严格的验收条件，双方通过文件往返，直到 Evaluator 标记 `AGREED`。

这一步的价值是：不要等做完以后才发现双方对“完成”的理解不同。

### 5. 评估器需要被校准

一个独立 Evaluator 并不会天然严格。它也可能宽容、误判、被表面完成度骗过去。

所以需要给它建立校准循环：

1. 给出少量正例、反例和边界案例。
2. 把每个评分维度拆成可观察信号。
3. 明确惩罚项，例如模板化输出、无法验证的声明、缺少核心流程、一眼 AI 感。
4. 要求评分解释和证据。
5. 阅读评估日志，找出它和人类判断不一致的地方。
6. 修改 rubric、prompt、权重或 few-shot。
7. 重跑同一个案例，再看日志。

评估器不是“写一个 prompt 就完事”的组件，它本身也要迭代。

### 6. 文件交接优先于长聊天

推荐使用短 artifact 交接：

```text
00-request.md
10-product-spec.md
20-evaluation-rubric.md
25-iteration-contract.md
25-final-review-contract.md
30-generation-report.md
35-context-transition.md
40-evaluation-report.md
50-final-summary.md
```

文件比长对话更适合作为 agent 间通信层：更简洁、可追溯、可复盘，也更不容易污染各自上下文。

### 7. 上下文重置不是压缩，而是换新实例

当 Generator 在长任务里开始丢状态、提前收尾或反复失败时，不要只把旧对话压缩给它继续做。

更稳妥的办法是启动一个新 Generator，并用 `35-context-transition.md` 交接：

- 当前目标
- 已完成工作
- 已变更文件或产物
- 当前合同
- 失败检查
- 下一步
- 仍然有效的约束

这相当于给模型一块干净的白板，而不是让它背着越来越重的历史继续工作。

### 8. Harness 组件必须可拆卸

每个组件都编码了一个假设：

- Planner 存在，是因为模型可能会低估或误解需求。
- Evaluator 存在，是因为生成者自评不可靠。
- Iteration contract 存在，是因为高层规格和可测试实现之间需要桥梁。
- Context reset 存在，是因为长上下文可能损害连贯性。

这些假设会随着模型能力变化而过时。正确做法不是一次砍掉一半流程，而是一次只移除或简化一个组件，对比质量、缺陷、成本、耗时和完成度。

如果质量不退步，就保留简化；如果质量下降或原因不清，就恢复组件。

## 完整模式与简化模式

### Full Cycle Mode

适合复杂、主观、高风险、容易漂移的任务。

流程是：

1. Planner 写 `10-product-spec.md`
2. Evaluator 写 `20-evaluation-rubric.md`
3. Generator 和 Evaluator 协商 `25-iteration-contract.md`
4. Generator 构建并写 `30-generation-report.md`
5. Evaluator 独立验收并写 `40-evaluation-report.md`
6. Coordinator 决定进入下一轮或结束

### Simplified Final Review Mode

只有当你通过 Component Audit 确认当前模型/运行时能稳定长时间工作时，才使用简化模式。

流程是：

1. 保留 Planner。
2. 在连续生成前冻结 `25-final-review-contract.md`。
3. Generator 连续完成更大范围任务。
4. Evaluator 最后统一严格评审一次。

简化模式可以移除逐周期结构，但不能移除 Evaluator。越接近模型能力边界，独立评估越重要。

## 安装

Claude Code：

```bash
mkdir -p ~/.claude/skills
cp -R skills/agent-harness ~/.claude/skills/agent-harness
```

Codex：

```bash
mkdir -p ~/.codex/skills
cp -R skills/agent-harness ~/.codex/skills/agent-harness
```

其他运行环境：

把 `SKILL.md` 作为核心方法文档，把 Planner、Generator、Evaluator、Coordinator 和文件产物映射到你的工具能力即可。默认模式是一个 agent 按顺序运行隔离角色轮次。

## 这个仓库和参考方法的关系

本仓库充分吸收了 harness engineering 实践中几个关键思想：克制的规划器、生成/评估分离、严格评估器、迭代合同、文件交接、上下文重置、评估器校准、组件消融和强模型后的流程简化。

同时，它做了自己的抽象：

- 改成平台中立 skill，而不是绑定某个具体运行时。
- 显式区分 Planner、Generator、Evaluator 角色轮次和 Coordinator。
- 把每个中间产物命名成可复用 artifact。
- 同时支持完整周期模式和最终统一评审模式。
- 提供中英双语说明，方便跨团队传播。

这不是一份照搬的提示词，而是一套可迁移的 AI 工作协议。
